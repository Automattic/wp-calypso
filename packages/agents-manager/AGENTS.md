# Agents Manager Package

`@automattic/agents-manager` is the shared component library for WordPress.com's AI agent experience. It runs in Calypso, the multi-site Dashboard, Simple and Atomic sites, the WooCommerce AI admin (self-hosted stores too) and Reader Chat on public blogs — all from the same source. Paths are relative to `packages/agents-manager/src/` unless they start with `apps/`, `packages/` or another repo's root.

## Architecture

- **Frontend** lives here (`packages/agents-manager/`) and is bundled by `apps/agents-manager/`.
- **Backend** is Jetpack's `projects/packages/agents-manager/` package. New API endpoints or loading contexts go there, not here.
- **Extension providers** (Big Sky, the Jetpack AI sidebar, WooCommerce AI, the Jetpack AI Hub) register via the PHP filter `agents_manager_agent_providers`. The loading flow crosses repos: PHP injects provider URLs → `loadExternalProviders()` dynamically imports them → they export `toolProvider`, `contextProvider`, etc. See `extension-types.ts` and `LoadedProviders` in `utils/load-external-providers.ts` for the provider contract.
- **Hosts** drive the chat from outside the React tree through `window.__agentsManagerActions` and window events — see `hooks/custom-actions/README.md`.
- **Chat runtime** comes from `@automattic/agenttic-client` (hooks, auth, message types) and `@automattic/agenttic-ui` (UI components, renderers). Both live in this repo under `packages/` and are also published to npm. Image Studio, the Jetpack AI sidebar, the Odie and Zendesk support clients, A8C for Agencies and parts of Calypso use them too: keep a change there backward compatible, with new behavior opt-in, and remove an old API only once none of them uses it.
- **Interactive UI** renders with `@automattic/ai-ui-renderer` (the A2UI runtime, the basic or shared components and their styles), and Agents Manager hosts it from `interactive-ui/` — see "Interactive UI" below.
- **Other docs**: the package root's `README.md` (usage, props, window API) and `SITE-CREDITS.md` (the site credits exports), plus the `README.md` beside the code it covers: `interactive-ui/` (the interactive UI architecture), `webmcp/` (the dev-mode browser tools, exposed through their own allowlists rather than the route settings) and `hooks/use-agent-layout-manager/` (dock layout).

```bash
# agenttic packages: test, then rebuild — Agents Manager type-checks and bundles their dist/
yarn workspace @automattic/agenttic-client test

```

## Conventions

These are the standard for new and changed code, even where older code falls short. Don't rewrite untouched code just to comply.

### Package rules

- **Imports**: Take React APIs from `@wordpress/element` (bare `react` for types only), UI from `@wordpress/components` and icons from `@wordpress/icons`; chat UI comes from `@automattic/agenttic-ui`. Don't add a new UI dependency.
- **i18n**: Use `@wordpress/i18n` with the global `__i18n_text_domain__`, unquoted: `__( 'Close', __i18n_text_domain__ )`. Fill placeholders with `sprintf()` and markup with `createInterpolateElement()`, never by joining translated pieces; use `_n()` for counts, and add a `/* translators: */` comment. Text only the model reads stays untranslated English: an ability's `description`, its schema text, and the `error` passed to `errorResult()`.
- **Curly quotes**: Preserve `“”` `‘’` exactly as they appear. Do not convert to unicode escapes or ASCII equivalents.
- **Tracks**: Record events through the helpers in `utils/tracks.ts` (`recordAgentsManagerTracksEvent()`, or `recordBigSkyTracksEvent()` for Big Sky parity events), never `recordTracksEvent` directly. They honor the tracking opt-out and add the shared props. Send ids and counts (`message_length`), never message text, page content or other user data. Before adding an event, prefer a new property value on an existing one (`surface` on `calypso_agents_manager_ai_chat_clicked`). Write event names in full at the call site, give each property one meaning (`link_type`, not `type`), and add a per-turn event to `TURN_EVENTS`. New event and property names need Tracks registration, so flag them in the PR. Keep `jetpack_big_sky_*` events and their properties as they are: they mirror Big Sky's.
- **Styles**: Prefix CSS classes with `agents-manager-`, BEM-style with kebab-case modifiers (`agents-manager-resolved-edit-action__status--reverted`), so they don't collide with wp-admin and editor styles. Import stylesheets last, after the JS modules, so the bundle puts your rules after the ones they override.
- **Accessibility**: Make every control a real button (`Button` from `@wordpress/components`, or `<button type="button">` for a custom-styled one) and every link to a page outside the chat an `<a>` with `href`; in-chat screens change through `navigate()` from a button. Never use a clickable `div`, except a backdrop that closes something. Give icon-only buttons a translated label.
- **Untrusted content**: Agent replies and page content are untrusted. Render them as text or through agenttic-ui's message renderers, never with `dangerouslySetInnerHTML`. Pass a URL they carry through `uriTransformer()` before it becomes an `href`, and check that a navigation target is same-origin, as `wp-admin-navigate` does.
- **Tests**: Put unit tests in the area's `__tests__/` folder (`components/__tests__/chat-header.test.tsx`, `abilities/<name>/__tests__/`), one behavior per test, named after what it checks. Query the UI by role or label as a user would; `getByTestId` is the last resort. Jest runs every file directly in `__tests__/`, so fixtures go in a subfolder. Give a new file with real logic a focused test (for moved code, see Extract before extending). A fix or behavior change to code a test runs, or to a hook a component suite mocks, adds a case that fails without it; for a mocked hook, in the hook's own test.

### Code quality

Write for the next reader: code that is readable, consistent and easy to change.

- **Keep it simple**: Make the smallest change that solves the problem at its cause. Don't add options or abstractions nothing uses yet, and don't duplicate logic: compute each condition once, in one place.
- **Consistency**: Follow the patterns already there (naming, file layout, data flow, error handling), so the codebase reads as one; where a rule here sets a different standard, follow the rule.
- **Structure**: Keep components thin, so they mostly wire things up and render. A behavior with effects or several pieces of state goes in a hook named after it, under `hooks/`; logic with no React state is a pure function in `utils/`. Simple local UI state can stay in the component. Features should grow by adding hooks and utils, not by growing components. Heavily shared components have stricter rules below.
- **Reuse**: Before writing a helper, hook or component, search `hooks/`, `utils/`, `components/`, `@wordpress/*` and agenttic for one that already does it. Extract shared code once a second caller needs it, not before.
- **Package APIs**: Use a dependency's API instead of hand-rolling what it does: `clsx()` for conditional class names, and in tests Jest's `it.each`, `expect.objectContaining()` and `jest.spyOn()`, with mocks restored.
- **No deprecated APIs**: Use the current API, not a deprecated one, such as a Button's `size="small"` instead of `isSmall`, or Sass's `@use` instead of `@import`. Fix any deprecation warning in code you touch.
- **Placement**: Put code where a reader would look for it: components in `components/<name>/`, hooks in `hooks/`, pure functions in `utils/`, contexts in `contexts/` and abilities in `abilities/<name>/`. A subsystem with its own lazy seam and doc keeps its pieces together in its own folder instead (`abilities/`, `interactive-ui/`); wherever this doc says `hooks/` or `utils/`, that folder counts too. A constant, type or helper one module uses stays in that module, exported from there when another needs it (`CREDITS_LOW_BALANCE` in `utils/credits.ts`). What an area shares goes in its `constants.ts` or `types.ts` (`abilities/constants.ts`), and what the whole package shares in the root ones; `utils/` holds functions, not files of constants or types.
- **Docs**: Put a doc beside what it covers: a folder's doc is its `README.md` (`interactive-ui/README.md`), and only docs about the whole package stay at its root (`README.md`, `SITE-CREDITS.md`). Each doc covers one topic: keep what belongs to it there, and move anything else to the doc it belongs to.
- **Names**: Say what a thing holds or does, in full words (`message`, not `msg`; `id` and `url` are fine). Booleans read as questions (`hasProviderSuggestions`), functions start with a verb (`syncProviderMetadata`), components are nouns (`ChatHeader`), hooks start with `use`, and files are kebab-case. Name unexplained numbers and repeated strings as module-level `SCREAMING_SNAKE_CASE` constants (`IMAGE_COLOR_TIMEOUT`). Rename what a change makes inaccurate.
- **Functions**: Return early instead of nesting, avoid nested ternaries, and give each function one job. If a block needs a comment to say what it does, make it a named helper.
- **Comments**: Explain why (a rationale, a gotcha, a cross-repo link), never what the code already says or how it changed. Keep them short, and update or delete them with the code.
- **Blank lines**: Separate the steps of a function or test with a blank line, not every statement.
- **State**: Never mutate state, props or store data; create new values. Derive what you can during render instead of copying it into more state and syncing it with an effect. The chat stays mounted across session, conversation and site switches, so key state, refs and caches that belong to one by its id, or reset them when it changes. Module-level state outlives the chat itself: use it only when it must, key it by the scope it belongs to, and say its lifetime in a comment. Key `sessionStorage` entries by every scope they belong to, as `utils/agent-session.ts` does with user, site and agent, and wrap each access in try/catch.
- **Effects**: Clean up everything an effect starts (listeners, timers, subscriptions, requests) in its cleanup function, and drop async results that land after the session or inputs changed. The chat mounts and unmounts inside host pages, so leaks outlive it.
- **Errors**: Never swallow an error. Recover where you can and tell the user what failed (an ability returns `errorResult()` so the agent can); `console.error` the rest with an `[AgentsManager]` prefix. Don't leave `console.log` calls in.
- **Exports and types**: Use named exports in new files, except a component loaded through `lazyComponent()` or `lazyWithRetry()`, which needs a default export. Use `unknown` with narrowing instead of `any`. Import from where a thing is defined, not through a local re-export. Only `index.ts` (the public API) and lazy-loading seams (a facade such as `abilities/index.ts`, or a module a lazy chunk loads) re-export.

### Every PR

- **Testing instructions**: Every PR MUST include testing steps, one section per environment the change runs in: Calypso (`yarn start`), the Dashboard (`yarn start-dashboard`), and the `widgets.wp.com` bundles for Simple/Atomic, WooCommerce AI and Reader Chat (sandbox `widgets.wp.com`, then `cd apps/agents-manager && yarn dev --sync`). Shared code runs in all of them; editor-only code (behind `isEditorPage()`) runs only in block editors, through the `widgets.wp.com` bundles. A change that keeps behavior (a rename or a move) says so and lists regression checks only. After the setup steps, list:
  - **Must test**: One case per behavior the PR changes, each with the expected result. Leave out anything unit tests already prove.
  - **Regression checks (optional)**: Nearby flows the change could affect, such as other surfaces, existing features and other agents' chats.
- **Deploy dependencies**: Every PR MUST include a `## Deploy dependencies` section naming the PRs in other repos (Big Sky, Jetpack, WooCommerce AI, wpcom) it needs and the order they must land in, or "None." Merged isn't live everywhere: Simple and Atomic can serve different Big Sky versions, and self-hosted sites run any Jetpack version, so name the version or condition each target needs.
- **Docs move with the code**: A change MUST update every doc that describes it, in the same PR: `README.md` and `AGENTS.md` files, other Markdown, docblocks and comments. Search the whole repo for the names you changed (files, exports, props, classes, flags) instead of relying on memory, and check again before finishing.
- **Changes clean up after themselves**: A change or removal MUST update or remove everything it leaves behind, in the same PR: callers, types, tests, mocks, styles, dependencies and code nothing uses any more. Search the whole repo again before finishing; only the references you mean to keep should remain. Callers include importers elsewhere in this repo (`git grep -l @automattic/agents-manager -- client packages apps`); run their tests too. Before changing or removing anything other repos read (the provider contract, `window.__agentsManagerActions`, window events, the `agentsManagerData` inline data typed in `global.d.ts`, the client context built in `utils/create-agent-config.ts`), also search Big Sky, Jetpack, WooCommerce AI and wpcom. While a deployed build still reads it, keep it, and say in the PR description when it can go.
- **Before requesting review**: Review and test your own PR first, and mark it ready only once all of this passes:
  1. **Code quality**: Read the whole diff as a reviewer would, against every rule in this doc. It should be correct, simple, and free of redundant or dead code.
  2. **Automated checks**: Run the unit tests, type-checks and lint from "Testing" above.
  3. **Manual testing**: Run every must-test case and any regression checks you listed yourself, in every environment the change runs in, so nothing regresses or breaks.

## Heavily shared components

The heavily shared components are `components/orchestrator-chat`, `components/agent-chat` and `components/agent-dock`: rendered by multiple agent chats and surfaces, they accrete cross-cutting logic fast. Target shape, as in `orchestrator-chat`: a thin composition layer — hooks in data-flow order under short section comments, glue only where two hooks meet, render at the bottom.

These MUSTs apply to every change to the state, effects, handlers, props or behavior of these components:

1. **One mechanism, one hook.** All state, refs, effects, and callbacks implementing a single behavior MUST live together in one custom hook under `hooks/`, named after the behavior (`use-image-upload`, `use-navigation-continuation` are the pattern). A mechanism's pieces MUST NOT be spread across the component body. The one exception: a step that needs the output of a hook called later goes in a new hook after that one, fed the first hook's outputs, never inline — as `useCheckpointAvailability` needs `messages` from `useCredits`, so it runs after `useCredits` and takes `getCheckpointMessage` from the earlier `useStreamedCheckpointMessages`.
2. **Logic grows in hooks, not inline.** A change MUST NOT add a React or `@wordpress/data` hook call (`useState`, `useRef`, `useEffect`, `useMemo`, `useCallback`, `useSelect`, …) to these components, only calls to hooks in `hooks/`, and MUST NOT add a branch to a callback several mechanisms share (`onTaskUpdate`, send, regenerate) — however small, Tracks included. Only simple UI state and glue between hook values are exempt. Extend the hook that owns the behavior, not a parallel one; a shared callback calls a step that hook returns (`recordTaskUpdate( update )`).
3. **Extract before extending.** To change a mechanism still inline in one of these components, first move all of it into its hook without changing behavior — the untouched-code exemption doesn't cover a mechanism you change. A move MUST keep the call order of hooks with effects (provider hooks such as `useSuggestions` may have effects of their own) and leave the component's test unchanged and passing. Don't move logic into a module that test mocks, or mock the new hook: the suite would pass without running it. Code the suite runs may use only the exports a mocked module's mock defines (`hooks/use-checkpoint-action`'s, for one); the rest are `undefined` there. Moved code needs no new test while that suite runs it.
4. **Pure logic goes to `utils/`.** New or changed logic with no React state — parsing, formatting, list transforms — MUST be a pure function in `utils/` with explicit inputs and outputs, not a module-level helper in the component file. A new stage of a multi-stage derivation (e.g. the `useMemo` shaping the transcript) MUST be a named pure function, so the derivation stays an ordered pipeline.
5. **Keep hook APIs narrow.** A hook MUST take explicit inputs and return only what callers use. When two mechanisms share state, it MUST be passed explicitly between them — never coupled through the component closure.
6. **One gate per surface difference.** Each surface, agent or provider difference MUST have one named gate, reused everywhere: a `utils/` predicate for a surface or agent (`isEditorPage()`, `isReaderChatAgent()`, `isCanvasWritingAgent()`), or a `ProviderCapabilities` flag for a provider, read from the `capabilities` prop. Give a new flag its own branch in `mergeCapabilitiesInto()` (`utils/load-external-providers.ts`) that defines how loaded providers combine: an opt-in such as `supportsRegenerateAction` is on if any provider opts in, and an opt-out of a default feature must not win while another loaded provider supports it. Never compare agent ids, provider ids, hosts or URLs inline, and pass a derived value down instead of re-deriving it, as `orchestrator-chat` passes `isReaderChat` to its hooks. Behavior owned by a provider MUST come through the contract, not be hardcoded in shared code; `isWooAiProvider()` predates this rule, so don't add callers; the temporary WooCommerce abilities in `abilities/woocommerce/` are the one exception, removed with them.
7. **Changing existing behavior needs a blast-radius check.** A shared component's props, events, and observable behavior are a contract with every surface. Before changing or removing any, you MUST find all consumers — every chat entry, and external providers if the provider contract (`extension-types.ts`, `LoadedProviders`) is involved (see Changes clean up after themselves) — and confirm each still behaves as intended.
8. **Docblock the why.** Every hook MUST have a docblock stating which mechanism it implements and why it exists — the race, product behavior, or platform quirk. That context is what keeps grouped logic safe to move later.

## Performance

One source ships to every surface, so weight one surface needs is weight they all carry — `reader-chat` most of all, since it bundles its dependencies instead of externalizing them.

- **Heavy, surface-specific code MUST load on demand, behind its gate.** A component goes through `lazyComponent()` (`utils/lazy-component.ts`) and renders behind its surface check (`{ isEditorPage() && <SelectedBlock /> }`) — without the check it fetches its chunk on every surface. A chat component in a catalog, or in the converter's `AM_COMPONENTS`, is gated by what renders it instead: its chunk loads only when a surface or message shows it. A catalog component goes through `lazyWithRetry()` instead, since the renderer supplies its `Suspense` and error boundary; where it also renders outside a surface, as the pickers do in `AM_COMPONENTS`, wrap it in `withLazyBoundary()`. Any other module goes behind a facade that owns its `import()` and retries a failed load on the next call, as `abilities/index.ts` and `utils/canvas-capture/index.ts` do. Name the chunk `/* webpackChunkName: "am-<name>" */`, and import only types from the lazy module: one value import puts it back in every entry.
- **No static editor imports in the shared chat path.** The shared chat path is every module an entry reaches through value imports without crossing an `import()` (`lazyComponent()`, `lazyWithRetry()`, a facade, the `am-webmcp` load in `hooks/use-webmcp-tools.ts`). A static import of `@wordpress/block-editor`, `blocks`, `core-data`, `media-utils` or `abilities` (bundled, so it adds bytes to every entry) MUST NOT be added there, directly or through a util or hook. Read editor stores by name (`select( 'core/editor' )`), not through an imported `store`, and use `import type` for type-only imports. `__tests__/shared-chat-path.test.js` enforces this for the package's own files; the build comparison below catches a dependency that starts importing them.
- **Measure before and after** a change that adds a dependency or touches a lazy seam: run `yarn build` in `apps/agents-manager`, then compare the `dist/*.min.js` sizes (`reader-chat.min.js` above all) and the `dependencies` in `dist/*.asset.json`. On the externalized entries, a `@wordpress/*` import adds a script handle WordPress enqueues wherever the entry loads, not bytes — even one only a lazy chunk reaches, since webpack moves externals into the entry chunk. So `import()` saves bytes in bundled entries such as `reader-chat`, not handles. Import chains are easy to misjudge by reading.

## Abilities

The editor abilities (`abilities/editor-abilities.ts`) load as an async chunk on editor pages only, behind the facade in `abilities/index.ts`.

- **The backend route settings decide scope** (`wpcom` repo, `wp-content/lib/ai/agents/route-settings/wp-orchestrator/`). Client-side registration never makes an ability callable: a new one also needs a paired wpcom PR that allows it in these route settings or has a server ability emit it. Link that PR in the description.
- **Provider order decides execution** — tool calls resolve first-write-wins by ability name, and `amToolProvider` runs first.
- **Add an ability** as a folder under `abilities/` plus an entry in `EDITOR_ABILITIES`, or in the facade's `ALL_SURFACE_ABILITIES` for a light ability every surface needs. Shared chat code reaches the editor chunk only through the facade; the few `abilities/` modules it imports directly (`ability-name.ts`, `stream-page-design/stream.ts`, `editor-navigate/page-path.ts`) MUST import nothing from the editor. For a summary of its result to show in the chat, add its `normalizeAbilityName()` form to `DISPLAYABLE_TOOL_MESSAGE_TOOL_IDS` (`utils/tool-message-utils.ts`); the converter drops unlisted tool messages. If it writes to whichever page the editor has open, or moves the canvas, add it to `CANVAS_BOUND_ABILITIES` or `CANVAS_MOVING_ABILITIES` (`utils/canvas-guard.ts`). New chat UI goes in a catalog (see "Interactive UI" below); the converter's `AM_COMPONENTS` holds only the components `show-component` messages render, until they move (AM-119).
- **Return `successResult()` / `errorResult()`** (`abilities/ability-result.ts`) — the backend reads that envelope.
- **Never rename an ability** — the route settings match on the name, so a rename silently drops it everywhere.
- **Guard callbacks that change editor state** with an `isEditorPage()` early return, as `set-site-logo` does.
- **Validate arguments in the callback** — nothing enforces the `input_schema` at runtime: a stringified `"false"` is truthy, and an empty object arrives as `[]`.
- **Resolve block ids with `resolveClientId()`** — the agent knows blocks by the short ids AM's page context hands out (`utils/block-ids.ts`).
- **Take checkpoints through `withCheckpoint()`** (`utils/checkpoints.ts`), with `toolId` set to the ability's `normalizeAbilityName()` form:
  - A write that lands later or outside a callback (a picker pick, the streamed page design) uses `setCheckpoint()` guarded by `hasCheckpoint()`, taken while the state is still the user's.
  - A new domain needs a scoped key, a snapshot/restore and redo support.
  - A write records through the `CheckpointRecorder` it is handed: `markWritten( key )` once it changes a `MID_BATCH_KEYS` domain (blocks, custom CSS, site title, site metadata), or that domain's undo is silently dropped, and `capturePageRename()` / `captureMenu()` as it reaches pages and menus. A test that mocks `withCheckpoint()` hands the write a recorder and asserts these calls.
  - A batch returns a partial failure instead of throwing, so the checkpoint survives.

## Interactive UI

Agents Manager hosts interactive UI surfaces from `interactive-ui/`. Its `README.md` has the architecture, where each piece lives, and the rules surfaces and catalog components follow: read it before changing either.

- **Add a component to `AGENTS_MANAGER_CATALOG`** (`interactive-ui/catalogs.ts`), not to the converter's `AM_COMPONENTS`.
- **Keep the renderer in its lazy chunk:** import only types from `@automattic/ai-ui-renderer`, and values only from its `capabilities` entry. `use-interactive-ui.ts` loads the renderer and its `style.scss` together.

## Pitfalls

- **Two deployment targets**: Shared code must work both in the SPAs (Calypso and the Dashboard) and in the `widgets.wp.com` bundles (Simple, Atomic, WooCommerce AI, Reader Chat). They use different bootstrap paths.
- **Async chunks load from the entry script's URL** (webpack's default `publicPath: "auto"`). Verify a new lazy seam on every target where its gate passes, `reader-chat` included, and check that its chunk request returns 200 — a failed load shows only as a missing feature and an `[AgentsManager]` console error. Chunk naming across the shared `dist/` is covered in `apps/agents-manager/AGENTS.md`.
- **asset.json sync gap**: Adding/removing `@wordpress/*` dependencies changes `.asset.json` files, which Jetpack's PHP reads from the server handling the request and caches for an hour — not from your synced bundle. To test such a change, sandbox the Simple site too; on Atomic and self-hosted sites it takes effect only after a deploy.
- **Unregistered script handles**: `@wordpress/*` packages WordPress doesn't register as scripts (e.g. `@wordpress/abilities`, `@wordpress/ui`) must stay force-bundled in `apps/agents-manager/webpack.config.js` — an externalized unregistered dependency, even one only a lazy chunk imports, makes `WP_Scripts` silently drop the whole bundle.
- **`reader-chat` route stubs**: `getReaderConfig` in `apps/agents-manager/webpack.config.js` aliases `components/agent-dock`'s exact imports of `'../agent-history'`, `'../support-guide'` and `'../zendesk-chat'` to a stub, keeping them out of the public blog bundle. Moving or renaming those imports puts that code back in, so update the aliases with them. It also aliases `@automattic/zendesk-client` to `reader-chat-zendesk-client-stub.js`, which exports only `useGetZendeskConversations`: importing another name from that package in code `reader-chat` reaches fails the build until the stub exports it. Don't import `smooch` directly there; it isn't aliased.
- **Message components outlive their turn**: A message's `component` parts stay in the transcript after later turns, `addMessage` ones included. A component that offers a choice for the current turn disables or hides itself once the user replies past its message (`getLatestUserMessageIndex()` in `utils/latest-message.ts`), as the pickers and the editor suggestion list do. Interactive UI surfaces go stale automatically (`interactive-ui/README.md`).
- **Help Center overlap**: The Help Center and the floating chat can both be open; the one touched last stays on top (`hooks/use-raise-on-focus.ts`).
- **The chat needs its stylesheet**: `useAgentLayoutManager` creates the portal node hidden, and only `components/agent-dock/chat-ui.scss` reveals it (`.agents-manager-chat { display: block !important }`), so a site that unloads the stylesheet gets no chat instead of an unstyled one over the page. Keep that rule with the portal's layout rules.
- **Host UI can render after the chat**: Learn about host UI the client renders late (the Calypso and Dashboard masterbar button) from a host prop, as `hasMasterbarAiChatButton` does, not a DOM lookup when the chat mounts; only server-rendered markup such as the wp-admin bar is safe to query. Host code that calls `window.__agentsManagerActions` waits for `agents-manager-ready` or checks `isReady` (`hooks/custom-actions/README.md`).
